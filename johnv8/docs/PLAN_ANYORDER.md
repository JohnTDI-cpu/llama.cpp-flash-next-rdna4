# Plan any-order z hazardami (sędzia workflow, 2026-09-03)

## Wybór
Design 1 ("konserwatywny") is the base: whitelist-driven grants, revoke-at-source safety nets (pool alloc, q8 cache, hcb scratch, cuBLAS, non-kernel stream ops), one tracker per ggml_backend_cuda_context, dry-run mode, staged rollout. Borrowed from Design 2: (a) an own inline hipExtLaunchKernel wrapper that returns hipError_t (hipExtLaunchKernelGGL discards it); (b) per-graph statistics counters; (c) converting the intra-device cudaMemcpyAsync/2D copies in cpy.cu into tracked copy kernels as an optional stage-2b item; (d) the observation that decisions must depend only on addresses and issue order (deterministic) so the scheme stays capture-safe if a future ROCm retains the flag. Rejected from Design 2: the ring rewrite of the VMM pool (drops the LIFO invariant, touches every pool user; decode-hot pool users are only mmvq/quantize, which stage 3 handles with a targeted q8 arena), the try_fuse dry-run/extent machinery (~30 macro sites, double matching) and the graph_optimize reorder pass (deferred to an optional stage 5, gated by dry-run numbers). Decisive verified facts that shape the plan: ROCm 7.2.4 CLR drops the flags argument at capture (ihipExtLaunchKernel does not store it; GraphKernelNode has no launchFlags_; replay uses flags=0) and the local anyorder_graph test confirms 16.2 us/kernel replay regardless of the flag, so any-order is applied only with HIP graphs disabled and every stage is an A/B against the graphs-on baseline; the graphs-off regime is close to CPU-issue-bound (~9-10 us CPU per dispatched node vs ~7.6 us GPU per launch), so E0e gates the whole effort before stage 1 lands.

## Streszczenie (PL)
Wybieram projekt konserwatywny (whitelista + odwolanie grantu u zrodla) jako baze, z kilkoma zapozyczeniami z projektu pelnego: wlasny inline hipExtLaunchKernel zwracajacy blad, liczniki statystyk, opcjonalna zamiana wewnatrzurzadzeniowych memcpy w cpy.cu na sledzone jadra oraz wymog, by decyzje zalezaly tylko od adresow i kolejnosci wydawania (deterministycznie). Zweryfikowalem klucz: pula VMM to alokator bump z asercja LIFO (ggml-cuda.cu:576-687), wiec nastepny wezel dostaje ten sam adres scratch, gdy poprzednie jadro moze jeszcze biec - dlatego alloc puli odwoluje grant. W zrodlach CLR ROCm 7.2 (ihipExtLaunchKernel -> ihipGraphAddKernelNode) argument flags jest porzucany, GraphKernelNode nie ma pola na flagi, a replay uzywa flags=0; lokalny test anyorder_graph.hip potwierdzil 16,2 us/jadro niezaleznie od flagi, wiec any-order dziala tylko przy wylaczonych grafach HIP i kazdy etap jest A/B wobec bazy z grafami (40,05 t/s bez MTP, 62,8/67,0 z MTP na 2 GPU). Kopie schedulera (cpy_tensor_async na strumieniu zrodla + event) i synchronizacje dzieja sie poza graph_compute, wiec wystarcza bariera na starcie splitu (poison) i jadro-join na koncu splitu, aby ostatni pakiet na strumieniu byl barierowy. Tracker (zakresy bajtow written/read od ostatniego launchu barierowego) mieszka w ggml_backend_cuda_context, po jednym na GPU, z wskaznikiem thread_local aktywnym tylko wewnatrz graph_compute; grant jest jednorazowy i konsumuje go pierwszy launch przez ggml_cuda_kernel_launch, kazdy kolejny launch wezla jest barierowy. Ukryte bufory (sloty q8cache, scratch hcblock yq/yq2/lo/licznik) sa deklarowane przez declare(), a sciezki hipBLAS, mmq, mmf i mmvq (do etapu 3) odwoluja grant; makra cudaMemcpyAsync/Memset/EventRecord/StreamSync w vendors/hip.h ida przez wrappery, ktore najpierw robia join, a potem zatruwaja tracker. Etapy: 0 (infrastruktura, tryb dry z licznikami, bez zmiany zachowania), 1 (mmvf + elementwise, ~390 kandydatow/token), 2 (jadra fuzyjne hc, rms_norm, rope, gdn, cpy, ~600), 3 (mmvq z arena q8 per graf zamiast puli LIFO, ~540), 4 opcjonalnie (maski zapisu, reorder w graph_optimize, powrot do grafow po aktualizacji ROCm z launchFlags_). Bramki: identyczne logity dry vs off, harness bit-exact [k]/[d] i test-backend-ops dla kazdego etapu, tryb stress z jadrem spin, asercje w commit(); wycofanie to GGML_HIP_ANYORDER=0 (kod bezczynny) lub opcja CMake. Najwiekszym ryzykiem nie sa wyscigi, lecz rezim bez grafow: przy ~9 us CPU na wezel (~20 ms/token) dekod jest bliski granicy CPU, wiec realny wynik to raczej 25 -> 20-22 ms/token (46-50 t/s bez MTP) niz pelne odzyskanie 11-13 ms luk z profilu. Najpierw uruchamiamy tanie eksperymenty: E0b (czy event/sync po any-order czeka na wszystko), E0c (kopie vs any-order), E0f (koszt CPU hipExtLaunchKernel), E0e (serwer z grafami off: sciana vs suma jader vs czas CPU) i dopiero po etapie 0 E0d (sufit grantow per etap w trybie dry).

Consequences: (1) any-order and HIP graphs are mutually exclusive on this ROCm; the switch must auto-disable capture. (2) An in-order launch is a full join of the stream, so the tracker only has to remember reads/writes since (and including) the last in-order launch. (3) The graphs-off regime is near CPU-issue-bound (~2226 x ~9 us = ~20 ms/token CPU vs 17-21 ms GPU kernel time), so the realistic ceiling is max(CPU issue time, kernel time), not "kernel time"; hipExtLaunchKernel is also cheaper on the CPU (2.10 vs 2.96 us measured for empty kernels), which helps that bound.

## 1. Data structures

All in `common.cuh`, compiled only under `GGML_USE_HIP && GGML_HIP_ANYORDER`; on CUDA/MUSA the API compiles to inline no-ops.

```cpp
struct ggml_cuda_ao_range { uintptr_t lo, hi; };            // half-open device VA range

struct ggml_cuda_anyorder {
    enum mode_t { OFF = 0, DRY = 1, ON = 2 } mode = OFF;     // from GGML_HIP_ANYORDER = 0 | dry | 1
    cudaStream_t stream0 = nullptr;                          // ctx.stream(device, 0)
    // launches issued since (and including) the last barrier launch on stream0
    std::vector<ggml_cuda_ao_range> written, read;           // reserve(512)
    // sets of the node/group currently being dispatched (+ declared extras)
    std::vector<ggml_cuda_ao_range> node_w, node_r;
    bool poisoned   = true;   // next kernel launch must be a barrier launch
    bool grant      = false;  // one-shot: consumed by the FIRST wrapper launch of the node
    bool node_open  = false;
    int  n_inflight = 0;      // any-order launches since the last barrier launch (0 => stream tail is a barrier packet)
    int  n_inorder_in_node = 0, n_other_in_node = 0, n_pool_in_node = 0, n_decl_in_node = 0;
    int  stage      = 0;      // whitelist stage from GGML_HIP_ANYORDER_STAGE (1..3)
    bool join_before_copies = true;   // GGML_HIP_ANYORDER_JOIN_COPIES (default 1 until E0b/E0c prove it unnecessary)
    // statistics (printed per 400 graphs when GGML_HIP_ANYORDER_STATS=1)
    uint64_t st_request = 0, st_grant = 0, st_conflict_raw = 0, st_conflict_war = 0, st_conflict_waw = 0,
             st_poisoned = 0, st_revoke_pool = 0, st_revoke_decl = 0, st_revoke_explicit = 0,
             st_join = 0, st_inorder = 0, st_anyorder = 0, st_grant_unconsumed = 0;
    uint64_t st_grant_by_op[GGML_OP_COUNT] = {}, st_req_by_op[GGML_OP_COUNT] = {};
};
```

Where it lives: one `ggml_cuda_anyorder ao;` member in `ggml_backend_cuda_context` (common.cuh ~1517, next to `q8cache`/`hcb`), i.e. one tracker per device/backend. A `thread_local ggml_cuda_anyorder * ggml_cuda_ao_cur` points to the active context's tracker only between `graph_compute` entry and exit (the sched thread alternates between the two devices strictly sequentially, so a pointer, not a copy). Outside `graph_compute` the pointer is null and every wrapper/macro behaves exactly as today.

Range extraction for a tensor `t`: `lo = (uintptr_t) t->data` (already includes `view_offs`), `hi = lo + (t->buffer ? ggml_backend_buft_get_alloc_size(t->buffer->buft, t) : ggml_nbytes(t))` -- the alloc size includes the `MATRIX_ROW_PADDING` bytes that mmvq/mmq read (ggml-cuda.cu:916-933) and the FA extra data; for strided views `ggml_nbytes` is the spanned extent (superset). Device VAs are unique per device, and the tracker is per device, so raw address comparison replaces Vulkan's `(buffer, offset)` pair.

## 2. Hazard model (Vulkan ggml-vulkan.cpp:15709-15770 transposed)

For a dispatched unit `nodes[i..i+n)` (n = 1 or the fused group): `W` = union of dst ranges of all n nodes, `R` = union of ranges of every non-null `src[j]` of all n nodes, plus extras declared by the op. Grant iff `mode != OFF && !poisoned && !overlap(W, written) && !overlap(W, read) && !overlap(R, written)` (WAW, WAR, RAW). Reads never conflict with reads. Comparison inside the unit is not needed. Elided fusion intermediates are included (conservative superset, exactly like Vulkan without `fused_ops_write_mask`; a write mask is a later refinement).

Tracker lifetime (F1): `written/read` hold the sets of every unit issued since, and including, the last barrier launch. `commit()`: if `n_inorder_in_node > 0 || n_other_in_node > 0` -> clear both vectors (that launch drained the stream); `poisoned = n_other_in_node > 0`; append `node_w -> written`, `node_r -> read`. Raw `<<<>>>` launches are invisible: they are barrier launches, but the tracker is NOT cleared for them (conservative: over-full tracker only produces extra in-order launches). Linear overlap scans over a few dozen ranges cost ~0.1-0.3 us per node, far below the launch cost.

Invariants: I1 a kernel is any-order only if its W/R pass the test against the sets of every launch since the last barrier launch; I2 the tracker holds a superset of those sets; I3 no any-order kernel touches pool memory or an undeclared hidden buffer; I4 the first kernel after any non-kernel stream op, and the first kernel of every `graph_compute`, is a barrier launch (poison); I5 when `graph_compute` returns, the last packet on the stream is a barrier packet (split-end join), and a join precedes every in-op event record / stream sync / (until E0b/E0c pass) memcpy/memset. Correctness argument: for kernels A (earlier) and B (later) on the stream, either B is a barrier launch (F1) or B is any-order and A is either before the last barrier launch L (completed before L started, visible via fences) or in the tracker (I2) and disjoint by I1. Non-kernel ops are ordered after earlier kernels by the AQL barrier/blit semantics and before later kernels by I4; their completion semantics rely on I5. Bit-exactness: kernels, arguments, grid shapes and every byte each kernel reads are unchanged; only the interleaving of provably disjoint kernels changes.

Whitelist (unfused nodes), `static bool ggml_cuda_ao_whitelisted(const ggml_backend_cuda_context&, const ggml_tensor * node, int stage)`:
- stage >= 1: `MUL_MAT`/`MUL_MAT_ID` when the new pure predicate `ggml_cuda_mul_mat_plan(ctx, node)` returns `PLAN_MMVF` (factor the decision chain of `ggml_cuda_mul_mat` 1823-1877 / `ggml_cuda_mul_mat_id` 1902-1950 into a side-effect-free enum {FWHT, CUBLAS, MMVF, MMF, MMVQ, MMQ, MMID_FALLBACK} used by both the dispatcher and the whitelist); `ADD/SUB/MUL/DIV` (binbcast.cu:440-470); `SCALE`; `UNARY` for ops routed through `unary_op_kernel` (exclude XIELU); `GLU` for ops routed through `unary_gated_op_kernel` (exclude SWIGLU_OAI / clamp variants, raw at unary.cu:383/449); `SQR/SQRT/SIN/COS/LOG`.
- stage >= 2: `RMS_NORM` (norm.cu:304-401, wrapper), `ROPE` when mode is NEOX/MULTI (rope.cu:433-486; `rope_norm`/`rope_vision` are raw), `GET_ROWS` with F32/F16/BF16 src0 (float path via wrapper; quantized is raw), `SET_ROWS` with float dst, `CPY/DUP/CONT` (kernel paths; the memcpy paths self-poison), `GATED_DELTA_NET`, `CONCAT` kernel path.
- stage >= 3: `MUL_MAT`/`MUL_MAT_ID` with `PLAN_MMVQ` (after the q8 arena, section 6).
Everything else (FLASH_ATTN_EXT, SOFT_MAX, ARGSORT/TOP_K, SUM/MEAN/CUMSUM, MMQ, MMF, cuBLAS, quantized get_rows/cpy/set_rows, moe_weighted_reduction/add_id until converted) is never requested.

Fused groups: `ggml_cuda_try_fuse` both matches and dispatches, so the request is made at the dispatch site, one line before the `ggml_cuda_op_*` call: `ggml_cuda_ao_request(*cuda_ctx, cgraph, i, n_nodes);`. Sites without the line never get a grant (safe default). Stage 1 sites: mmvf gate/up+GLU (ggml-cuda.cu ~3985, ~4025), mmvf+bias (~4180), fused add/mul (3691/3693, n = n_fuse), unary_mul (4260), relu_sqr (4265), scale_silu (4253), softcap (4311), shexp_tail (4306). Stage 2 sites: rms_norm family (4200/4205/4210/4215), rope+set_rows (3612), gdn fused cache (3526, n = 1 + nodes_to_skip), topk_moe (3585/3600), conv_snap (4233), hc_mix_collapse (4246), hc_combine (4280), hcblock_a (4286) + hcblock_b (4292) with declare, hc_combine_inject (4299). Stage 3: the mmvq fusion sites (~3832, ~3926, ~3996, ~4035, ~4123, ~4188).

Hidden buffers (F4) declare before their first launch: `hcblock_a` -> `declare(yq, yq_bytes, W)`, `declare(yq2, yq2_bytes, W)`, `declare(los, lo_bytes, W)`, `declare(cnt, 256, W)` (after hc-block.cu:406); `hcblock_b` -> `declare(H.yq2, yq2_bytes, R)` (before 442); q8 cache (stage 3) -> `insert()` declares the slot W, `find()` hit declares R. Revoke at source: `ggml_cuda_pool_vmm::alloc` and `ggml_cuda_pool_leg::alloc` call `ggml_cuda_ao_revoke(pool)` (a pool pointer must exist before the kernel that uses it, so revocation always precedes that launch); `ggml_cuda_mul_mat_vec_q` entry (stage 1-2), `ggml_cuda_mul_mat_q`, `ggml_cuda_mul_mat_f`, `ggml_cuda_op_mul_mat_cublas` entry (revoke + poison: hipBLAS kernels and workspaces are invisible), `ggml_cuda_mul_mat_id` fallback (revoke + poison; the host sync could also clear the tracker, optional).

Intra-node rule: only the FIRST wrapper launch of a unit consumes the grant; every later wrapper launch of the unit is a barrier launch (waits for the first and everything else). Whitelisted ops must not issue a raw `<<<>>>` before a wrapper launch (a raw launch cannot consume the grant, so the following wrapper launch would overlap it). Debug: `commit()` warns when a granted node produced zero wrapper launches and zero other ops (`st_grant_unconsumed`).

## 4. Launch wrapper and macro wrappers

`ggml_cuda_kernel_launch` (common.cuh:1767-1792), HIP branch before the `<<<>>>` fallthrough:
```cpp
#if defined(GGML_USE_HIP) && defined(GGML_HIP_ANYORDER)
    if (ggml_cuda_anyorder * T = ggml_cuda_ao_cur; T && T->mode == ggml_cuda_anyorder::ON && launch_params.stream == T->stream0) {
        const bool ao = T->grant; T->grant = false;
        if (ao) { T->n_inflight++; T->st_anyorder++; } else { T->n_inorder_in_node++; T->n_inflight = 0; T->st_inorder++; }
        CUDA_CHECK(ggml_cuda_hip_ext_launch(kernel, launch_params, ao ? hipExtAnyOrderLaunch : 0, std::forward<Args>(args)...));
        return;
    }
#endif
```
`ggml_cuda_hip_ext_launch` is a copy of the 10-line body of `hipExtLaunchKernelGGL` (hip_ext.h:141-153: `validateArgsCountType` + `pArgs` marshalling, identical to what `<<<>>>`/`hipLaunchKernelGGL` do, so implicit conversions and by-value structs such as `ggml_cuda_mm_fusion_args_device`/fastdiv values behave identically) that returns the `hipError_t` of `hipExtLaunchKernel`. `vendors/hip.h` adds `#include <hip/hip_ext.h>`. Stage 0 keeps `<<<>>>` for non-granted launches (zero behavioural change); an optional later toggle routes all launches through `hipExtLaunchKernel(flags=0)` if E0f shows a CPU saving. Assert in debug: `ctx.curr_stream_no == 0` when a grant is consumed.

Non-kernel stream ops: `vendors/hip.h` macro lines 58 (`cudaDeviceSynchronize`), 65 (`cudaEventRecord`), 81 (`cudaLaunchHostFunc`), 86-89 (`cudaMemcpy`, `cudaMemcpyAsync`, `cudaMemcpyPeerAsync`, `cudaMemcpy2DAsync`), 95 (`cudaMemsetAsync`), 119 (`cudaStreamSynchronize`), 120 (`cudaStreamWaitEvent`) are redirected to `static inline` wrappers at the end of `common.cuh` that call `ggml_cuda_ao_before_stream_op(stream)` and then the HIP function (the wrappers are no-ops when `ggml_cuda_ao_cur == nullptr` or the stream is not `stream0`, so the buffer interface on `cudaStreamPerThread` and everything outside `graph_compute` is untouched). `cudaEventRecord`/`cudaStreamSynchronize`/`cudaDeviceSynchronize` always join first (F6); memcpy/memset join only while `join_before_copies` is set.

Split boundaries: `ggml_backend_cuda_graph_compute` (4627-4685) calls `begin_graph` after `q8cache.bump()` and `end_graph` before returning (also on the capture path, where the tracker stays inert because `mode` is forced OFF when `use_cuda_graph`). Because I5 makes the stream tail a barrier packet, `event_record` (4687), `cpy_tensor_async` (2486), `synchronize` (2545) and the sched's `ggml_backend_synchronize` keep their in-order meaning on both GPUs; the split-start poison makes the first kernel of every split a barrier launch, which cannot overtake the destination stream's `cudaStreamWaitEvent` (F5).

Activation conditions (all must hold): env `GGML_HIP_ANYORDER` in {1, dry}; build flag `GGML_HIP_ANYORDER`; `GGML_CUDA_CC_IS_RDNA3(cc) || GGML_CUDA_CC_IS_RDNA4(cc) || GGML_CUDA_CC_IS_CDNA(cc)` (hip_ext.h:67: flag unsupported on GFX9); `curr_stream_no == 0` and no `GGML_CUDA_GRAPH_OPT` concurrent event active; HIP graphs disabled for this context. Enforcement of the last point: when `GGML_HIP_ANYORDER=1`, `ggml_cuda_graph::is_enabled()` (common.cuh:1258) returns false (log once) exactly as `GGML_CUDA_DISABLE_GRAPHS` does, so capture never begins and the wrapper never calls `hipExtLaunchKernel` inside a capturing stream. The launcher therefore runs either graphs-on/in-order (today) or graphs-off/any-order.

## 5. Staged rollout, checkpoints, gates

Bit-exact gate (every stage): (a) `GGML_HIP_ANYORDER=dry` vs unset: identical logits and identical grant statistics between two runs (tracker path exercised, launches unchanged); (b) stage N ON vs OFF: the existing harness + server bit-exact gates ([k],[d]) on >= 3 prompts x 512 tokens, greedy, fixed seed, plus token-by-token logit compare; (c) stress: same comparison with a second process keeping the GPU busy and with `GGML_HIP_ANYORDER_STRESS=1` (an any-order 50 us spin kernel is launched before each granted launch to widen the overlap window); (d) `test-backend-ops -b HIP0` in any-order mode vs CPU (per-op whitelist mistakes); (e) debug asserts in `commit()` (granted node with zero wrapper launches, launch stream != stream0, curr_stream_no != 0). Performance gate: median of 4 x tg128 (prose/code) on 2x GPU, graphs-on/in-order baseline (E54: 40.05/40.02 t/s no MTP; 62.8/67.0 with MTP) vs graphs-off/any-order stage N; wall time from the server timings (rocprof forces completion signals per packet and hides overlap; use it only for kernel durations).

3. 7. GFX9 unsupported; gate on cc; env default off.

# Projekt: konserwatywny

## overview
Goal: let provably independent kernels on the single per-device stream start without the AQL barrier bit (hipExtAnyOrderLaunch), keeping every existing kernel, launch site and memory layout unchanged. Hardware/runtime model the design relies on (HSA AQL semantics that <<<>>> already depends on): (F1) a packet WITH the barrier bit starts only after ALL preceding packets in the queue have completed; (F2) a packet WITHOUT the barrier bit may start as soon as the command processor reaches it, i.e. it may overlap with every packet issued after, and including, the most recent barrier-bit packet; (F3) every packet keeps its own acquire/release fences, so anything completed before a barrier packet is visible to packets issued after it; (F4) memcpy/memset/event/sync commands remain in-order with respect to everything before them. Consequence: an in-order launch is a full join of the stream, and a hazard tracker only has to remember reads/writes of the launches issued since (and including) the last in-order launch.

The scheme (mirrors Vulkan's unsynced_nodes_written/read at <repo>/ggml/src/ggml-vulkan/ggml-vulkan.cpp:15709-15770, but instead of inserting barriers where hazards exist, it removes the barrier only where none exists):
1. Per-backend-context tracker (lives in ggml_backend_cuda_context, one per device): vectors of byte ranges `written`, `read` accumulated since the last in-order launch, plus `poisoned` (next launch must be in-order) and counters.
2. Whitelist-driven request: before a node (or a fused group) is dispatched, the eval loop / the try_fuse dispatch site calls ggml_cuda_anyorder_request(ctx, cgraph, i, n). It computes W = dst ranges of nodes[i..i+n), R = src ranges, and grants only if !poisoned and W does not overlap (written U read) and R does not overlap written. A grant is a thread-local one-shot flag.
3. The launch wrapper ggml_cuda_kernel_launch (common.cuh:1767-1792) consumes the flag on its FIRST launch and uses hipExtLaunchKernelGGL(..., hipExtAnyOrderLaunch); every subsequent launch of that node (and every non-whitelisted node, raw <<<>>> launch, cuBLAS call) is a normal barrier launch, which is a full join.
4. After the node: ggml_cuda_anyorder_commit(ctx, cgraph, i, 1+nodes_to_skip) clears the grant; if any in-order wrapper launch or non-kernel stream op happened during the node the tracker is cleared (that launch drained everything before it), poisoned is set if a non-kernel op happened; then the node's W and R (plus extras declared by the op) are appended. Supersets are always safe: extra entries can only add barriers.
5. Safety nets that make whitelist mistakes degrade to in-order rather than to races: pool alloc revokes the grant (pool memory is LIFO-reused across nodes); q8cache / hcb scratch / cuBLAS paths revoke or declare their hidden ranges; the vendors/hip.h macros for cudaMemcpyAsync/cudaMemcpy2DAsync/cudaMemcpyPeerAsync/cudaMemsetAsync/cudaEventRecord/cudaStreamWaitEvent/cudaStreamSynchronize/cudaLaunchHostFunc are redirected to inline wrappers that first launch a tiny in-order "join" kernel when any-order kernels are in flight, then call HIP, then poison the tracker.
6. Split boundaries: at graph_compute entry the tracker is cleared and poisoned (first launch of every split is a barrier launch, which covers scheduler input copies and event waits); at graph_compute exit a join kernel is launched if any any-order kernel was issued since the last in-order one, so outside graph_compute the last packet on each stream is always a barrier packet and all HIP "last command" shortcuts (event record, stream sync, cross-device copies) keep their normal meaning.
7. Any-order is only active when: env GGML_HIP_ANYORDER=1, build flag GGML_HIP_ANYORDER, device is RDNA3/RDNA4/CDNA (hip_ext.h:67 documents the flag as unsupported on GFX9), curr_stream_no == 0, no GGML_CUDA_GRAPH_OPT concurrent event active, and either HIP graphs are off or stage-0 experiment E0a has shown the flag survives stream capture. A dry-run mode (GGML_HIP_ANYORDER=dry) runs the full tracker and counts would-be grants per op class per token without changing any launch, which measures the ceiling of each stage at zero risk.

## hazard_model
Ranges. A tensor t maps to the half-open device byte range [t->data, t->data + size) with size = ggml_backend_buft_get_alloc_size(t->buffer->buft, t) when t->buffer is set (ggml-cuda.cu:916-933: ggml_nbytes plus MATRIX_ROW_PADDING padding for quantized types, exactly the padding mmvq/mmq read; same helper the existing fusion check uses at ggml-cuda.cu:2993-3011), else ggml_nbytes(t). Device virtual addresses are unique per device, so raw address comparison replaces Vulkan's (vk_buffer, offset) pair; the tracker is per device so two devices never compare. ggml_nbytes on non-contiguous tensors (permute/transpose views, strided KV views) returns the spanned extent, so a view's range is the region it can touch (superset for strided views, fine). t->data already includes view_offs (set by ggml-alloc), so views need no special-casing.

Sets per dispatched group nodes[i..i+n): W = union of dst ranges of all n nodes; R = union of ranges of every non-null src[j] of all n nodes; plus extras declared by the op (hidden scratch, see pool_buffers). Nodes skipped by the loop (ggml_cuda_is_view_or_noop at ggml-cuda.cu:2565, GGML_TENSOR_FLAG_COMPUTE == 0 at 4466) launch nothing and add nothing, as in Vulkan.

Rules (Vulkan ggml-vulkan.cpp:15738-15756 transposed): grant any-order iff !poisoned && overlap(W, written) == false && overlap(W, read) == false && overlap(R, written) == false. This covers RAW (R vs written), WAR (W vs read), WAW (W vs written). Reads vs reads never conflict. Comparison against the node's own sets is not needed (a node only conflicts with other in-flight launches).

Tracker lifetime: `written`/`read` hold the sets of every launch since, and including, the most recent barrier launch on the stream. commit(): if n_inorder > 0 or n_other > 0 during the node -> clear both vectors (F1: that launch waited for everything before it), poisoned = (n_other > 0); then append W, R, extras. Raw <<<>>> launches are not counted (they are barrier launches, but the tracker is not cleared; this is conservative: an over-full tracker only produces extra in-order launches). Vectors are small (a few dozen ranges between barriers) so linear overlap scan is cheaper than the launch itself; reserve() them once.

Allocator aliasing: ggml-alloc reuses memory of dead tensors within a graph, so two different tensors can share bytes; that is why the key is the byte range, not the tensor pointer (Vulkan does the same and its is_src_of also treats same-base views as dependent, ggml-vulkan.cpp:18027-18050).

In-place ops and views: for GGML_OP_CPY the node is a view of src[1] (dst->data == src[1]->data), ADD/SCALE/UNARY in place have dst->data == src[0]->data, SET_ROWS/ROPE-fused write into KV-cache views. In all cases W = dst range and R = src ranges; the intra-node overlap is irrelevant, the cross-node check catches: an earlier in-flight reader of the same bytes (WAR, e.g. flash-attn reading the K view while a set_rows into the same cache region is dispatched), an earlier writer (RAW/WAW). Nothing else is needed: a view node itself never launches.

Scheduler inputs (ggml-backend.cpp:1679-1800): tensors copied into the split backend by cpy_tensor_async (ggml-cuda.cu:2489-2555: memcpy on the SOURCE device stream, cudaEventRecord on it, cudaStreamWaitEvent on the destination stream) or by synchronous ggml_backend_tensor_copy, before ggml_backend_graph_compute_async (1803). Handling: graph_compute entry clears the tracker and sets poisoned, so the first kernel of every split is a barrier-bit packet, which cannot start before the barrier-AND packet of the event wait completes (F1). Inputs are leafs inside the split and only ever read, so nothing else is required. Outputs consumed by the next split are read by cpy_tensor_async after graph_compute returned, i.e. after the split-end join (see launch_sites), so the memcpy sees completed data.

Non-kernel stream ops (cudaMemcpyAsync/cudaMemsetAsync/2D/Peer): they are in-order on the stream with respect to earlier packets (blit kernels carry the barrier bit; SDMA copies are gated by a barrier packet), so they can never race with earlier any-order kernels. The problem is the other direction: a LATER any-order kernel could overlap a still-running blit kernel and the copied bytes are not tensors known to the tracker (mmvq padding memset at mmvq.cu:1464, cpy memcpy path cpy.cu:474-478, set/get_tensor_async ggml-cuda.cu:2446-2460, mmq/fattn internals). Rule: poison -> the next kernel launch on that stream is in-order, which drains the copy, so its byte ranges never need to be tracked. Additionally the wrapper launches a join kernel BEFORE the copy if any-order kernels are in flight (see launch_sites for why).

Per-device state: the tracker and counters live in ggml_backend_cuda_context (one sched thread drives both devices' streams alternately, so thread-local counters would mix streams); a thread_local pointer `cur` to the active context is set at graph_compute entry and in each backend-interface function, the grant flag is thread-local (only meaningful between request and the first launch of one node).

## pool_buffers
The VMM pool (ggml-cuda.cu:543-690) is a strict LIFO bump allocator: alloc returns pool_addr + pool_used (668-670), free asserts ptr == pool_addr + pool_used (687). Every op's temporaries are freed at op end (RAII ggml_cuda_pool_alloc, common.cuh:1176-1216) and the NEXT pool user gets the same addresses while the previous user's kernels may still be running. Such WAR/WAW hazards are invisible to a tensor-range tracker, so the invariant is: every kernel that touches pool memory is a barrier launch (F1 then guarantees the previous user has finished). Enforcement at the source, not by whitelist: ggml_cuda_pool_vmm::alloc (578-671) and ggml_cuda_pool_leg::alloc (470-521) call ggml_cuda_anyorder_revoke() (grant=false, n_pool++). Because a pool pointer must exist before the kernel that uses it is launched, revocation always precedes that launch. This covers ggml_cuda_pool_alloc users (mmvq.cu:1470, mmq.cu, fattn-common.cuh:999, softmax.cu:358, cpy, top-k.cu:227, argsort.cu:279, sum.cu:37, mean.cu:48, cumsum.cu:234, mmf.cu:78-80, cross-entropy-loss.cu:113, ggml_cuda_op_mul_mat cublas paths) without touching them. Note: a pool user is still tracked normally at commit (its dst/src ranges), so a later independent node can be any-order and overlap with the pool user's kernel; that is safe because whitelisted kernels never touch pool memory.

Persistent hidden device buffers (cudaMalloc'd once, reused across nodes and graphs, not visible as tensors) found by grep: (a) johnv8_q8_cache slots (common.cuh:1435-1477): mmvq on a cache hit (mmvq.cu:1477-1481) launches mul_mat_vec_q reading a slot written by an earlier node's quantize kernel, with NO pool alloc, so nothing would revoke; (b) johnv8_hcb_scratch (common.cuh:1481-1498): hcblock_a (hc-block.cu:391-425) writes yq, yq2, lo copy, and an atomic "last block" counter; hcblock_b (427-449) reads yq2; the same buffers are reused by every layer (WAR between hcblock_b of layer L and hcblock_a of layer L+1); (c) cuBLAS workspaces (common.cuh:1628) used by hipBLAS kernels (raw launches); (d) allreduce dev_tmp (allreduce.cu:522, tensor-split mode only). Rule: an op that touches such memory either revokes at entry (stage 1: one line at the top of ggml_cuda_mul_mat_vec_q mmvq.cu:1389, ggml_cuda_mul_mat_q, ggml_cuda_mul_mat_f, ggml_cuda_op_mul_mat/cublas paths) or declares the ranges through ggml_cuda_anyorder_declare_extra(ctx, {ptr, bytes, is_write}...) before its first launch. declare_extra re-runs the overlap test with the extra ranges against the tracker, revokes the grant on conflict, and remembers the ranges so commit() appends them. Stage 2 uses it for hcblock_a (W: yq, yq2, lo-copy, counter) and hcblock_b (R: yq2); stage 3 uses it for the q8 slot (W on miss, R on hit).

cudaMemcpyAsync/cudaMemsetAsync inside ops: in-order for everything before them (F4), so no danger backwards; forwards they are handled by poison (next launch in-order) plus the pre-copy join. For the design this means their byte ranges are never tracked and ops using them need no whitelist knowledge: GGML_OP_CPY can be whitelisted even though its contiguous path uses cudaMemcpyAsync (cpy.cu:474): when the memcpy path is taken, the macro wrapper poisons and the node simply gets no overlap; when the kernel path is taken it may be any-order. Cost of poison is one extra in-order launch per copy; copies are ~180/token but mostly at split boundaries which are barriers anyway.

Stage 3 replaces the pool for mmvq's q8 buffer by a per-graph arena: extend johnv8_q8_cache into a ring with enough slots for one whole split (no address reuse within a single graph_compute; reuse only across graph_compute calls, which are separated by the split-start barrier), so the quantize kernel and the matvec of different nodes never alias, and slot hits (same src1, e.g. q/k/v/gate/alpha/beta projections and shared-expert vs routed-expert inputs) turn the matvec into a single any-order launch.

## launch_sites
Wrapper change (common.cuh:1767-1792), HIP-only branch before the <<<>>> fallthrough:

hipExtLaunchKernelGGL uses the same validateArgsCountType marshalling as hipLaunchKernelGGL, so int->int64_t style implicit conversions that <<<>>> performs are preserved; it returns void and drops hipExtLaunchKernel's hipError_t, so either keep cudaGetLastError (as now) or copy its 10-line body into common.cuh and CUDA_CHECK the return. vendors/hip.h must add #include <hip/hip_ext.h>. The stream must be ctx->stream() with curr_stream_no == 0 (assert in debug); any-order is inactive while GGML_CUDA_GRAPH_OPT concurrent events are active (ggml-cuda.cu:4433-4460).

Thread-local handoff: `thread_local struct { bool grant; ggml_backend_cuda_context * cur; } g_anyorder;` grant is set only by request(), consumed by the first wrapper launch, and force-cleared by commit() whatever happened, so a grant can never leak into the next node. Per-device counters in the context: n_anyorder_inflight (since last barrier launch), n_inorder_in_node, n_other_in_node (memcpy/memset/event/sync/pool), n_pool_in_node.

Eval loop wiring in ggml_cuda_graph_evaluate_and_capture (ggml-cuda.cu:4462-4569): (1) at graph_compute entry (4627-4682): tracker.clear(); poisoned = true; g_anyorder.cur = cuda_ctx; active = env && cc ok && (!use_cuda_graph || capture_flag_verified); (2) fused path: request() is called inside ggml_cuda_try_fuse immediately before each whitelisted dispatch (list in multi_kernel_nodes), commit(cgraph, i, 1 + nodes_to_skip) is inserted at 4536 before the `i += nodes_to_skip; continue;`; (3) unfused path: `if (whitelisted(node)) request(cgraph, i, 1);` right before ggml_cuda_compute_forward (4563), `commit(cgraph, i, 1)` right after it; (4) at the end of evaluate_and_capture / graph_compute: if n_anyorder_inflight > 0 launch the join kernel through the wrapper (in-order), then g_anyorder.cur = nullptr. The E11 plan-cache branch (4475-4503) only decides whether try_fuse is called and is unaffected.

Raw launch sites that bypass the wrapper (safe: they are barrier launches, they just never benefit): getrows.cu:187,224 (quantized get_rows, i.e. the token-embedding lookup), norm.cu:286-300 (norm/group_norm), unary.cu:383,449,529, rope.cu:391-395,525-529 (rope_norm/vision), cpy.cu:258-385 (quantized cpy), set-rows.cu:107, add-id.cu:51, moe-weighted-reduction.cu:38, softmax.cu:291-380, snake.cu, quantize.cu:589-695 (mmq quantize), convert.cu, argsort/top-k. Whitelist rule for ops containing raw launches: allowed only if no wrapper launch can follow a raw launch inside the same op (otherwise the wrapper launch would take the grant and could overlap the raw one); in debug builds commit() warns when a granted node produced zero wrapper launches and zero other ops (a raw launch consumed nothing).

cuBLAS (ggml-cuda.cu:1553-1613, hipBLASLt kernels are raw launches): revoke + poison at ggml_cuda_op_mul_mat_cublas entry.

Non-kernel stream ops: redirect vendors/hip.h macros (line 58 cudaDeviceSynchronize, 65 cudaEventRecord, 81 cudaLaunchHostFunc, 86-89 cudaMemcpy/Async/PeerAsync/2DAsync, 95 cudaMemsetAsync, 119 cudaStreamSynchronize, 120 cudaStreamWaitEvent) to `static inline` wrappers in common.cuh: `if (g_anyorder.cur && g_anyorder.cur->n_anyorder_inflight) ggml_cuda_anyorder_join(cur);` then the HIP call, then `n_other_in_node++; poisoned = true`. The join kernel is `__global__ void ggml_cuda_anyorder_join_kernel() {}` launched with 1 block through the wrapper (barrier bit set) and costs ~3 us. Why the join is needed even though F4 holds: clr's hipEventRecord and hipStreamSynchronize can bind to the completion of the LAST queued command instead of enqueuing a marker (marker elision); with in-order streams "last command done" implies "all done", with any-order packets it does not, so ggml_backend_cuda_event_record (4687-4690, used by the scheduler after every split at ggml-backend.cpp:1843) or cpy_tensor_async's copy_event could fire early. The split-end join makes this moot for the backend interface; the in-wrapper join covers cudaEventRecord/cudaStreamSynchronize used inside ops (mul_mat_id fallback, allreduce, tensor-split mul_mat). Experiment E0b verifies the concern; if clr proves safe, the join before memcpy/memset can be dropped (keep the event/sync ones).

## multi_kernel_nodes
Fused groups (ggml_cuda_try_fuse, ggml-cuda.cu:3496-4316): the eval loop cannot know the group extent before try_fuse both matches and dispatches, so the request must be made at the dispatch site, one line per whitelisted fusion: `ggml_cuda_anyorder_request(cuda_ctx, cgraph, i, n_nodes);` immediately before the ggml_cuda_op_* call. Sites without the line simply never get a grant (safe default). Stage 1 sites: mmvf gate/up+glu fusions (3982, 4023), mmvf+bias (4181), fused_add/fused_mul (3691-3693), unary_mul (4260), relu_sqr (4265), scale_silu (4253), softcap (4311), shexp_tail (4306). Stage 2 sites: rms_norm fused family (4200, 4205, 4210, 4215), rope+set_rows (3612), gdn fused cache (3526), topk_moe (3585, 3600), conv_snap (4233), hc_mix_collapse (4246), hc_combine (4280), hcblock_a (4286), hcblock_b (4292), hc_combine_inject (4299). Stage 3: mmvq fusion sites (3832, 3926, 3996, 4035, 4123, 4188).

Declared sets of a fused group are the conservative superset W = dst of every node in [i, i+n), R = every src of every node in the group. Intermediates elided by the fused kernel (e.g. rms_norm output inside rms_norm+mul, the 7 intermediates of hc_combine, the argsort/view chain of topk_moe) are thereby marked written/read although the kernel never touches them; this only adds barriers when the allocator recycles those bytes soon after (accepted; can be refined later with a per-fusion write mask like Vulkan's fused_ops_write_mask). Outputs that are not the last node (topk_moe writes weights and ids, the gdn/conv snapshot cpy targets, set_rows into the cache view) are dst of nodes inside the group, so they are covered by construction. Hidden buffers are declared via declare_extra (hcblock A/B, q8 slot).

Multi-launch ops: only the first wrapper launch of a node/group is any-order; any further launch is a barrier launch (n_inorder_in_node++), which (F1) waits for the first launch and everything else, so intra-node dependencies (hcblock_a: hcblock_a0_f32 writes xn and yq, hcb_launch_a1 reads yq, hc-block.cu:415-422; stage 3 mmvq: quantize then mul_mat_vec_q) are respected without knowing them. commit() then clears the tracker (the barrier launch drained it) and appends the node's sets, so the NEXT node can again be any-order relative to the still-running second kernel if independent. The perf consequence is that only the first kernel of such nodes overlaps predecessors; hcblock_a is the only two-launch node in stage 2, mmvq-on-miss in stage 3.

Verified single-wrapper-launch ops for the whitelist (by reading the op bodies): mul_mat_vec_f (mmvf.cu:395-410 via ggml_cuda_mul_mat_vec_f 634-731, no pool/memset), binbcast add/sub/mul/div and fused variants (binbcast.cu:440-470; repeat_back at 407 is raw and not whitelisted), scale (scale.cu:18-19), unary_cuda / unary_gated_cuda (unary.cu:32-35, 21-24), softcap (softcap.cu:17-18), shexp_tail (shexp-tail.cu:149-153), scale_silu and hc_mix_collapse (hc-mix.cu:335-345, 464-474), hc_combine (hc-combine.cu:256-270), hc_combine_inject (475-490), hcblock_b (hc-block.cu:383-384), rms_norm family (norm.cu:310-401), rope_neox/rope_multi (rope.cu:433-486), rms_norm_mul_rope (820-844), gated_delta_net (gated_delta_net.cu:229-238, one launch per op, fused cache writes go to cpy-node dsts), topk_moe (topk-moe.cu:293-329), conv_snap (conv-snap.cu:114-117), set_rows float (set-rows.cu:212-213), get_rows float (getrows.cu:234 path), dsv4_hc_comb/pre/post (dsv4-hc.cu:215-285), cpy kernel paths (cpy.cu:201-242). Not whitelisted: anything with pool use (fattn, mmq, mmf, softmax large, argsort/top-k, sum/mean/cumsum), moe_weighted_reduction and add_id until their raw launches are converted to the wrapper (trivial, stage 2 optional), quantized get_rows/cpy/set_rows (raw, no gain), cuBLAS paths.

## graphs_and_multigpu
Evidence from ROCm 7.2.4 about any-order under stream capture: (1) hip_ext.h:95-153 and hip_runtime_api.h:7118-7140 document flags = hipExtAnyOrderLaunch for hipExtLaunchKernel/hipExtLaunchKernelGGL; hip_runtime_api.h:949 defines hipExtAnyOrderLaunch 0x01; hip_ext.h:67 says the flag is not supported on GFX9xx. (2) /opt/rocm-7.2.4/lib/libamdhip64.so.7.2.70204 contains the log strings "[hipGraph] Current capture node ExtLaunchKernel on stream : %p" and "... ExtModuleLaunchKernel ...", so hipExtLaunchKernel is intercepted during hipStreamBeginCapture and turned into a graph kernel node instead of failing. (3) The public node description hipKernelNodeParams (hip_runtime_api.h:1492-1499: blockDim, extra, func, gridDim, kernelParams, sharedMemBytes) has no flags field, and hipLaunchAttributeID (1570-1578) has no any-order attribute, so there is no public way to set, query or restore any-order on a graph node; whether the capture path stores the flag internally cannot be determined from headers or binary strings (no "anyorder" string in the library; the clr sources hip_graph.cpp / hip_graph_internal.cpp are referenced only by path). (4) The 7.2 graph executor does topology-driven scheduling: strings "ScheduleNodesIntoBatches: Total nodes = %zu, total segments = %zu max dependency level = %d, max streams = %d", "Creating %u parallel streams for device %d", env DEBUG_HIP_GRAPH_SEGMENT_SCHEDULING / DEBUG_HIP_FORCE_GRAPH_QUEUES / DEBUG_HIP_GRAPH_BATCH_SIZE, and "Complex graph detected: %zu segments, avg length %.2f - falling back to classic path". A graph captured from ONE stream is a linear dependency chain, so this scheduler cannot overlap anything in our graphs; only a retained per-node any-order flag could.

Experiment E0a (decides the whole graphs story, ~60 lines, reuse the existing 4000-kernel microbench): capture the 4000 any-order kernels-with-work into a hipGraph via hipStreamBeginCapture/EndCapture, hipGraphInstantiate, time hipGraphLaunch + sync; repeat after a hipGraphExecUpdate with changed kernel args (the backend uses cudaGraphExecUpdate at ggml-cuda.cu:2665-2686). ~2 us/kernel => flag retained: enable any-order during the capture pass (the eval loop with tracker runs exactly once per capture at 4348-4571 and the replay inherits the flags; also verify the update path keeps them, else force re-instantiate). ~17-59 us/kernel => flag dropped: any-order is applied only when use_cuda_graph is false, and stage results are an A/B of (graphs ON, in-order; current 62.8/67.0 t/s on 2 GPUs) versus (graphs OFF, any-order stage N). Also try DEBUG_HIP_GRAPH_SEGMENT_SCHEDULING=0/1 in E0a to know which executor path is active.

Critical caveat for the graphs-off regime: the eval loop costs ~11 us CPU per launch on HIP (your johnv8 timing), 2226 launches => ~24 ms/step of CPU issue time versus 17 ms of GPU kernel time, so without graphs the GPU is starved by the CPU regardless of barriers, and the 13 ms of GPU idle measured with graphs on is not the number any-order can recover there. Any-order pays off in graphs-off mode only if CPU cost per launch is driven below the GPU time per launch (~7.6 us average) – experiment E0e measures this; otherwise the win requires the flag to survive capture (E0a) or a fork/join capture (GGML_CUDA_GRAPH_OPT with the 2-GPU patch) that the clr segment scheduler can parallelize.

Multi-GPU (2x R9700 via ggml_backend_sched, one split per device transition): each backend has its own context, stream 0, pool and now its own tracker; the sched thread alternates between them, so all state is per context and only the `cur` pointer is thread-local. Cross-device traffic goes through cpy_tensor_async (ggml-cuda.cu:2513-2555: cudaMemcpyAsync or cudaMemcpyPeerAsync on the SOURCE stream, cudaEventRecord(copy_event) on it, cudaStreamWaitEvent on the destination stream), ggml_backend_cuda_event_record/wait (4687-4696) used by the scheduler (ggml-backend.cpp:1696, 1843) and ggml_backend_cuda_synchronize (2557). All of these happen outside graph_compute, where invariant I5 (split-end join) guarantees the last packet on both streams is a barrier packet, so events, waits and copies keep in-order semantics; inside a split the first launch is forced in-order by the split-start poison, so it cannot overtake the destination stream's event wait. GGML_CUDA_GRAPH_OPT fork/join (4743-4760) is only active with graphs on and a single device, so it is mutually exclusive with stages 1-3; if E0a is positive a stage 4 could combine both (per-stream trackers, one per curr_stream_no).

## correctness_argument
Assumptions (each checked by a stage-0 microbenchmark, all are the same properties <<<>>> already relies on): F1 barrier-bit packet starts only after all preceding packets in the queue completed; F2 non-barrier packet may start once the CP reaches it (this is exactly the 2.0 us vs 17-59 us measurement); F3 per-packet acquire/release fences make writes completed before a barrier packet visible to later packets; F4 memcpy/memset/event/sync commands are ordered after everything issued before them. Invariants maintained by the implementation: I1 a kernel is launched any-order only if its W does not intersect written U read and its R does not intersect written, where the sets describe every launch since and including the last barrier launch on that stream; I2 the tracker always holds a superset of those sets (commit appends supersets for every executed node, clears only when a barrier wrapper launch or a non-kernel op occurred in the node, and raw launches never clear); I3 no any-order kernel touches pool memory or an undeclared hidden buffer (revocation in pool alloc, revoke/declare at q8cache, hcb scratch and cuBLAS paths, whitelist inspection of remaining ops: single wrapper launch, src/dst only); I4 the first kernel after any non-kernel stream op or at split start is a barrier launch (poison); I5 when graph_compute returns, the last packet on the stream is a barrier packet (split-end join), and a join precedes every in-op event record / stream sync.

Claim: for any two kernels A (issued earlier) and B (issued later) on the same stream, either B starts after A completes, or A and B access no common byte with at least one write. Case 1: B is a barrier launch: F1. Case 2: B is any-order. Let L be the last barrier launch before B. If A was issued before L: A completed before L started (F1) and B was processed after L, so B starts after A completed; A's writes are visible (F3). If A was issued after or is L: A is in the tracker set (I2) and I1 guarantees W_B disjoint from A's reads and writes and R_B disjoint from A's writes, so both kernels' inputs and outputs are unaffected by the interleaving. Byte ranges are supersets of the bytes actually accessed (alloc size incl. quantized padding; spanned extent for strided views; whole-group dst/src union for fusions; declared scratch), so disjointness of ranges implies disjointness of accesses. Non-kernel ops: ordered after earlier kernels by F4; later kernels are ordered after them by I4; their completion semantics are correct by I5. Cross-device and scheduler input copies: I4 at split start and I5 at split end reduce them to the standard in-order case. Pool aliasing: I3. Allocator aliasing between dead and new tensors: byte-range keying. Bit-exactness: kernels, arguments, grid shapes and memory contents seen by each kernel are unchanged; the only kernel with cross-launch atomics is hcblock_a's scratch counter, which is declared W and thus never shared with an overlapping launch; hence every kernel computes exactly what it computes today.

Validation (all bit-exact requirements): (a) GGML_HIP_ANYORDER=dry vs off: identical logits (tracker code path exercised, no launch change); (b) stage N on vs off: token-by-token logit comparison over >=3 prompts x 512 tokens with greedy sampling and fixed seeds, plus the existing bench pairs; (c) stress: same comparison while a second process keeps the GPU busy (perturbs timing), and with GGML_HIP_ANYORDER_STRESS=1 which additionally launches a 50 us spin kernel any-order before each granted launch to widen overlap windows; (d) test-backend-ops with the HIP backend in any-order mode versus CPU (per-op, catches whitelist mistakes); (e) debug asserts in commit(): a granted node must have produced >=1 wrapper launch or a non-kernel op, launch stream == ctx->stream(), curr_stream_no == 0.

## staged_plan
Stage 0 (infrastructure + measurements, no behavioural change): implement tracker, request/commit, wrapper branch behind GGML_HIP_ANYORDER, macro wrappers, join kernel, and the dry-run mode. Experiments (microbenchmarks in the style of the existing 4000-kernel test): E0a graph capture retention (see graphs_and_multigpu); E0b event/sync semantics: 100 slow any-order kernels each writing a distinct buffer region, then one tiny any-order kernel, then hipEventRecord+hipEventSynchronize (and separately hipStreamSynchronize) followed by a host check of all regions – any incomplete region proves the marker-elision hazard and confirms the join is required; E0c memcpy/memcpyPeer issued after any-order kernels copies complete data (D2D and GPU0->GPU1); E0d run the model with GGML_HIP_ANYORDER=dry and print grants/token per op class for the stage-1/2/3 whitelists (ceiling of each stage at zero risk); E0e graphs off, in-order: wall time per step vs summed kernel time and CPU us per launch – decides whether the graphs-off regime can profit at all. Checkpoint: E0a/E0b/E0c results recorded; dry-run logits identical; grant ceiling per stage known.

Stage 1 (mul_mat_vec_f + elementwise): whitelist GGML_OP_MUL_MAT / MUL_MAT_ID when the dispatcher will take mmvf (mirror the predicate at ggml-cuda.cu:1844 / 1929-1934: src0 F32/F16/BF16, ggml_cuda_should_use_mmvf; otherwise no grant) plus revoke() at the entry of ggml_cuda_mul_mat_vec_q, ggml_cuda_mul_mat_q, ggml_cuda_mul_mat_f and the cuBLAS paths so a mis-predicted path is still in-order; ADD/SUB/MUL/DIV/ADD1 (binbcast), SCALE, UNARY (unary_cuda ops), GLU (unary_gated), SQR/SQRT/SIN/COS/LOG/CLAMP; fusion sites: mmvf fusions, fused_add/mul, unary_mul, relu_sqr, scale_silu, softcap, shexp_tail. Stage 2 (hc kernels + norms + the rest of single-launch ops): add RMS_NORM and its fused family, ROPE (neox/multi) and rope+set_rows, rms_norm_mul_rope, GET_ROWS/SET_ROWS float paths, GATED_DELTA_NET (+fused cache), conv_snap, topk_moe, hc_combine, hc_combine_inject, hc_mix_collapse, hcblock_a/b with declare_extra, dsv4_hc_*, CPY/DUP/CONT; convert moe_weighted_reduction and add_id raw launches to the wrapper. ## expected_gain
Inputs: 2226 launches/step, 17 ms kernel time, 13 ms GPU idle/step across both GPUs (graphs on), i.e. an average gap of ~5.8 us per launch, consistent with the microbenchmark (barrier-drain plus dispatch latency per packet). A granted any-order launch removes most of its own gap (its dispatch overlaps the predecessor's tail) and lets sub-10 us kernels run concurrently. 1. Regime risk (largest): graphs-off is CPU-bound at ~11 us/launch, so any-order without graphs may not beat the current graphs-on 62.8/67.0 t/s; mitigated by E0a/E0e gating before investing in stages 2-3.

9. Queue/CP resources: thousands of non-barrier packets in flight were fine at 4000 in the microbenchmark; watch for hipErrorOutOfResources on kernel-arg pools with graphs off.

# Projekt: pelny

## overview
GOAL: replace "every kernel packet carries the AQL barrier bit" (what <<<>>> does on ROCm 7.2.4: 17-59 us/kernel when kernels have work, ~5.8 us average idle gap x 2226 launches = ~13 ms/token) with a Vulkan-style scheme: a per-device hazard tracker decides, launch by launch, whether the kernel may be submitted with hipExtAnyOrderLaunch (barrier bit cleared, ~2 us/kernel, overlaps with in-flight kernels) or must be an ordered launch (barrier bit set = a full fence of everything issued before it on that HSA queue).

SHAPE OF THE DESIGN (mirrors ggml-vulkan: ggml_vk_sync_buffers = our ordered launch; unsynced_nodes_written/read = our epoch sets; ggml_vk_graph_optimize = our reorder pass):
1. Epoch model. On one HSA queue (ctx.stream(), stream 0 of the device) an ordered launch F is a fence: every packet before F completes before F launches, and every packet after F launches after F launched (packets launch in queue order). So the only launches that can be in flight together with a new launch L are the ones issued at or after the most recent fence. The tracker keeps exactly that set ("epoch") as byte ranges in device VA: written-since-fence and read-since-fence. L is any-order iff its write set overlaps nothing in the epoch and its read set overlaps no epoch write; otherwise L is ordered and becomes the new fence (epoch := L's ranges).
2. Complete read/write sets. Graph tensors (dst as read+write, all srcs as read, all nodes of a fusion unit), pool scratch (registered by the pool at alloc time), and persistent hidden buffers (q8 dedup cache slots, hc-block scratch, fattn f16 extra buffers, hipBLAS workspace) are all tracked as plain address ranges, so views, recycled ggml-alloc buffers and pool aliasing are handled uniformly (no ggml buffer/offset bookkeeping needed: one VA space per device).
3. Deterministic ring pool. The VMM pool becomes a ring under any-order mode so consecutive independent nodes get distinct scratch addresses (today the LIFO bump allocator hands every node the same bytes, which would force every pool-using node to be ordered). Wrap-around is detected by the tracker as an overlap and forces a fence. The ring is reset at every ggml graph compute, which keeps addresses deterministic (needed if HIP graphs ever coexist).
4. Single choke point. All launches go through ggml_cuda_kernel_launch (common.cuh:1767). In any-order mode it calls hipExtLaunchKernel with flags = 0 or hipExtAnyOrderLaunch, taken from the tracker: node-level decision computed by the eval loop before compute_forward/try_fuse (begin_unit), refined by scratch registrations that happen inside the op, and an intra-node policy: only the first launch of a unit may be any-order; every later launch in the same unit is ordered unless the op explicitly declares independence (ctx.ao.next_launch_any_order()). This is exactly "mmvq = [quantize writes tmp] -> [matvec reads tmp] -> second launch ordered after the first" without auditing 100 ops. Raw <<<>>> launches, hipBLAS/hipcub launches and cudaMemcpy/MemsetAsync are ordered by construction and only add ranges to the epoch (they never clear it), so they are safe and merely suboptimal until converted.
5. Reorder pass in ggml_backend_cuda_graph_optimize (runs per split before ggml-alloc allocation, like Vulkan's) clusters independent nodes into levels so that consecutive launches qualify, while keeping every ggml_cuda_try_fuse unit contiguous (units found with a dry-run mode of the same matchers). Because it runs before allocation, lifetimes extend and the allocator gives clustered nodes distinct memory (the same trick the existing fork/join optimizer relies on).
6. Graph boundaries. Each ggml_backend_cuda_graph_compute starts with tracker reset + forced ordered first launch (fence) + ring reset, and ends with an explicit ordered empty kernel (fence) so that everything the scheduler does between graphs (cudaMemcpyPeerAsync of split inputs, event record/wait, stream sync, D2H of logits) sees completed data regardless of ROCclr blit/SDMA internals.
7. HIP graphs and the multi-stream fork/join optimizer are mutually exclusive with any-order (auto-disabled when GGML_CUDA_ANY_ORDER=1). Our graphs are worth only +3-4% (CPU launch overhead), any-order attacks the 13 ms/token of GPU idle; hipExtLaunchKernel also has lower CPU cost per launch (2.1 vs 2.96 us measured), recovering part of what graphs gave.
Bit-exactness: only the relative timing of provably independent kernels changes; every kernel sees exactly the inputs it sees in serialized execution and intra-node kernel order is unchanged, so outputs are bit-identical.

## hazard_model
STATE (struct ggml_cuda_hazard_tracker, one per ggml_backend_cuda_context, valid for ctx.stream() only):
- struct range { uintptr_t lo, hi; }  (device VA, half-open)
- std::vector<range> epoch_w, epoch_r  : written / read by launches issued at or after the most recent fence (the fence launch included)
- std::vector<range> unit_w, unit_r    : ranges of the unit currently being issued (graph tensors + scratch registered so far)
- bool unit_needs_fence, scratch_needs_fence, force_fence_next
- int launches_in_unit; bool next_any_order_opt_in
- cudaStream_t stream; bool active     (thread-local pointer `ggml_cuda_ao_current` set by the eval loop; nullptr outside graph eval => legacy behaviour)
- stats: n_ordered, n_any_order, n_fences_scratch, n_ring_wraps, n_unknown_ops (GGML_CUDA_AO_STATS=1 prints per graph)

RANGE EXTRACTION for a node t: base = (uintptr_t) t->data (already includes view offset), size = ggml_nbytes(t) (for strided/permuted views ggml_nbytes is the byte span of the view, i.e. a conservative superset). dst is inserted into BOTH unit_w and unit_r (covers in-place ops, accumulate-into-dst, atomics into dst, partial writes into views; this adds no extra conservatism because WAW already forces order against prior writes). Every non-null src[j] into unit_r. For a fusion unit [i, i+k] all k+1 nodes contribute (intermediate nodes that are elided by the fused kernel are still added: conservative, safe; a per-fusion write mask like Vulkan's fused_ops_write_mask is a later refinement). Ranges of weights (GGML_BACKEND_BUFFER_USAGE_WEIGHTS buffers) are read-only and never written inside a graph, so they can be skipped from unit_r for speed after stage 1 (keep them in until AO_VERIFY passes).

DECISION RULE (needs_fence(unit) computed in begin_unit, re-evaluated on every scratch registration):
  ordered  iff  exists r in unit_w with overlap(r, epoch_w) or overlap(r, epoch_r)   [WAW, WAR]
            or  exists r in unit_r with overlap(r, epoch_w)                          [RAW]
overlap = interval intersection. Sets are small (everything since the last fence, typically 5-30 ranges), so a linear scan per range is ~0.1-0.3 us per node.

TRANSITIONS (performed inside the launch wrapper, so the epoch only changes when a launch really happened on the tracked stream):
- first launch of a unit: ordered = unit_needs_fence || scratch_needs_fence || force_fence_next. If ordered: epoch := unit ranges (clear then add). If any-order: epoch += unit ranges.
- subsequent launches in the same unit: ordered unless next_any_order_opt_in was set by the op since the previous launch. After an ordered launch: epoch := unit ranges (superset of "ranges touched at/after this fence" within the unit). After an any-order launch: epoch += unit ranges (no-op if already there).
- end_unit (eval loop, after compute_forward/try_fuse returns): if launches_in_unit == 0 (raw <<<>>> only, hipBLAS, hipcub, memcpy-only op): epoch += unit ranges, never clear (we cannot prove a fence happened; the op itself is ordered by construction, so it is safe; n_unknown_ops++).
- explicit fence: ggml_cuda_ao_fence(ctx) launches an empty kernel k_ao_fence<<<1,1>>> through the wrapper with force_fence_next = true; used at graph start/end and in paranoid mode.
- graph start (ggml_backend_cuda_graph_compute): tracker.reset(); force_fence_next = true; pool.ring_reset(). Graph end: ggml_cuda_ao_fence(ctx).

IN-ORDER NON-KERNEL OPS (cudaMemcpyAsync/Memcpy2DAsync/MemsetAsync on ctx.stream(), hipEventRecord, hipStreamWaitEvent, hipStreamSynchronize): they are in-order stream commands (blit kernels with barrier bit or SDMA copies bracketed by barrier-AND packets in ROCclr) and are modelled as ordered ops that touch [dst,dst+n) (w) and [src,src+n) (r). They are wrapped in helpers ggml_cuda_memcpy_async(ctx, dst, src, n, kind) / ggml_cuda_memset_async(ctx, ...) that (a) register ranges into unit_w/unit_r, (b) mark launches_in_unit as "unknown" (no clear), and (c) in any-order mode, for intra-device contiguous copies, substitute a copy kernel launched through the wrapper (so the copy itself can be any-order and be a proper tracked launch). Under GGML_CUDA_AO_PARANOID=1 a non-kernel op whose ranges overlap the epoch is preceded by an explicit fence kernel (removes any reliance on ROCclr blit/SDMA ordering; cost only where a copy really depends on in-flight any-order kernels).

INTRA-NODE DECLARATIONS available to ops (all no-ops when the tracker is inactive):
- ctx.ao.touch_write(ptr, n) / touch_read(ptr, n): register hidden buffers (q8 cache slot, hc scratch, f16 K/V conversions, hipBLAS workspace).
- ctx.ao.next_launch_any_order(): the next launch in this unit does not depend on the unit's previous launches (used only where an op issues provably independent kernels, e.g. a future batched multi-matvec; currently no hot op needs it).
- ctx.ao.stream_synced(): op did a stream sync (mul_mat_id fallback) => epoch can be cleared (optional optimisation).
The eval-loop side: begin_unit(cgraph, i, i+k) before try_fuse/compute_forward, end_unit() after; k comes from a dry-run of ggml_cuda_try_fuse (see multi_kernel_nodes) or, in stage 1, from the conservative rule "if try_fuse might fuse here, treat the unit as ordered".

MULTI-STREAM: the wrapper compares launch_params.stream with tracker.stream; launches on any other stream (ggml_cuda_op_mul_mat row-split streams, allreduce.cu streams, GGML_CUDA_GRAPH_OPT fork streams) are always flags=0 (ordered on their own queue). Any-order mode asserts curr_stream_no == 0 and disables GRAPH_OPT.

## pool_buffers
WHY POOL TRACKING IS THE CRUX: ggml_cuda_pool_vmm::alloc (ggml-cuda.cu:576-668) is a bump allocator, free() (670-679) asserts LIFO and rewinds pool_used. Every op's ggml_cuda_pool_alloc RAII frees at op end, so node N+1's scratch lands at exactly node N's address. With the tracker alone this is correct (WAR/WAW overlap => ordered) but every pool-using node (mmvq quantize buffers, fattn dst_tmp/meta/KV_max, softmax tmp, argsort/top-k temp storage, mul_mat_id sorting buffers, cuBLAS to_fp16 temporaries, get-rows-less MoE buffers) would be forced ordered. Hence:

RING MODE (ggml_cuda_pool_vmm, enabled when GGML_CUDA_ANY_ORDER=1; VMM is available on gfx1201 per the device log; the legacy pool ggml_cuda_pool_leg gets the same ring logic or any-order is refused without VMM):
- Layout: [ring: GGML_CUDA_AO_RING_MB, default 64 MB] [LIFO bump area for big allocations, grown/mapped exactly as today]. Physical memory for the ring is mapped on first use with the existing cuMemCreate/cuMemMap code (granularity-rounded).
- alloc(size): size rounded to 128 B (as today). If size <= ring_size/4: if cursor + size > ring_size then cursor = 0 (n_ring_wraps++); ptr = ring_base + cursor; cursor += size; call tracker->on_scratch(ptr, size): adds [ptr, ptr+size) to unit_w and unit_r and sets scratch_needs_fence if it overlaps epoch_w or epoch_r (this is how a wrap-around, or the rare case of two units sharing a slot, forces the next launch to be a fence: after the fence nothing older is in flight, so reuse is safe). Else (big allocation, prefill mmq/mmq-id buffers, dequant temporaries): allocate from the bump area, register the same way and additionally set scratch_needs_fence = true unconditionally (big-area addresses repeat immediately; conservative).
- free(ptr, size): ring allocations: no-op except a live-count for debugging (the LIFO assert is dropped for ring blocks); big-area: unchanged LIFO rewind.
- ring_reset(): cursor = 0; called at graph compute start right after tracker.reset() and the forced start fence, which guarantees that nothing from the previous graph is still in flight when addresses are reused. This also makes addresses deterministic per graph (the same node sequence yields the same scratch addresses each token), which the tracker's decisions rely on for reproducibility and which is required if any-order is ever combined with HIP graph capture.
- Sizing: decode temporaries are tiny (q8_1 of one 4096-token row = 4.5 KB; fattn tmp = parallel_blocks*n_head*DV*4 B; top-k/argsort temp storage for the router logits a few KB); a 64 MB ring holds thousands of allocations per token, so wraps happen at most a few times per token and each costs one fence. Report n_ring_wraps in AO_STATS; make the ring larger if it wraps often. VRAM cost: +64 MB per device.

HIDDEN PERSISTENT BUFFERS (outside ggml tensors and outside the pool) that must register ranges:
- johnv8_q8_cache (common.cuh:1435-1475): insert() returns a slot that the quantize kernel writes; subsequent mmvq nodes in the same graph read it (find()). Round-robin eviction (N=6) can hand a slot to a new src1 while an any-order matvec of an earlier node may still read it. So: insert() -> ctx.ao.touch_write(slot, cap) (sets scratch_needs_fence if the slot is in the epoch), find() hit -> ctx.ao.touch_read(slot, bytes). Because reuse of a slot is at least 6 quantizes later and fences are frequent, in practice this never forces extra fences. The graveyard buffers are never reused, fine.
- johnv8_hcb_scratch (common.cuh ~1480-1500; used in hc-block.cu:404-426): yq, yq2, lo copy, counter (int zeroed by the kernel). Both hcblock A (writes) and B (reads yq2/lo) register them; the hidden dependency A->B (hcb_last_lo) is then visible to the tracker as an ordinary RAW on yq2, and layer l+1's A (writing yq/yq2) is ordered against layer l's B if it is still in the epoch.
- fattn f16 extra buffers (ggml_cuda_flash_attn_ext_get_f16_extra_data, used in launch_fattn fattn-common.cuh:1000-1030 for non-f16 K/V): persistent per context; register as write in the conversion and read in the fattn kernel.
- hipBLAS workspace (ggml_backend_cuda_context::cublas_workspaces): only ever touched by rocBLAS kernels, which are always ordered; no registration needed but document it.
- hipcub temp storage in argsort/top-k comes from the pool (tracked automatically); hipcub's own kernel launches are raw (ordered).

GENERAL RULE: any code path that obtains device memory other than through a graph tensor or the pool must call touch_write/touch_read before its first launch, and the code review for any-order mode grep-checks cudaMalloc/cuMem* sites in ggml-cuda for that.

DEFAULT INTRA-NODE POLICY: first launch of a unit may be any-order (per tracker), every later launch in the unit is ordered. This is correct for every multi-launch op in the tree without per-op declarations, because in all of them launch n+1 consumes what launch n produced. Ops opt in to any-order for a later launch only via ctx.ao.next_launch_any_order().

PER-OP ANALYSIS (decode-hot first):
- mmvq (mmvq.cu:1389 ggml_cuda_mul_mat_vec_q): [optional cudaMemsetAsync of src0 padding, only for COMPUTE-usage src0: never for weights] -> quantize_row_q8_1_cuda (writes pool ring slot or q8cache slot) -> mul_mat_vec_q_switch_type (reads slot + weights, writes dst). Declared deps: matvec after quantize (default policy). With the q8 dedup cache (GGML_JOHNV8_Q8_DEDUP, on by default) a group of k matvecs on the same src1 becomes: Q(fence) M1(ordered: reads the slot written in the epoch) M2(any-order: the slot's write is before fence M1) ... Mk(any-order). So k parallel projections cost 2 ordered launches instead of k+1, and the quantize of the next independent node overlaps the matvec of the previous one (Q2 any-order while M1 runs, M2 ordered). Chains (o_proj after attention) stay ordered, as they must.
- mmvq with ids (MoE experts, decode path via ggml_cuda_mul_mat_id -> ggml_cuda_mul_mat_vec_q with ids): same two launches; ids tensor is a src (written by topk-moe) and tracked.

## graphs_and_multigpu
HIP GRAPHS (USE_CUDA_GRAPH, ggml_backend_cuda_graph_compute 4629-4690, ggml_cuda_graph_evaluate_and_capture 4318-4610):
1. Can the any-order flag be captured? hipExtLaunchKernel is a symbol in libamdhip64 (confirmed by strings) but whether CLR has a stream-capture hook for it, and whether hipKernelNodeParams keeps the flags, is not knowable from headers (hipKernelNodeParams has no flags field). Even if capture succeeded, a single-stream capture produces a linear dependency chain, and CLR's graph exec re-derives ordering from that chain (packet-capture mode replays kernel packets with the barrier bit on a linear chain; branchy graphs go to parallel streams with signal-based joins that cost more than the barrier-bit bubble). So the flags cannot usefully survive capture; that is consistent with our graphs giving only +3-4% (they remove CPU launch cost, not GPU drain bubbles).
2. Decision: any-order and HIP graphs are mutually exclusive, enforced in code: when GGML_CUDA_ANY_ORDER=1, ggml_cuda_graph_set_enabled returns false (log once) so graph_compute never begins capture and the wrapper never calls hipExtLaunchKernel inside a capturing stream (calling a non-capturable API during capture would invalidate the capture with hipErrorStreamCaptureUnsupported). The same switch disables GGML_CUDA_GRAPH_OPT (fork/join multi-stream optimizer, which needs graphs and 1 device anyway) because the tracker is per-queue and any-order subsumes it: it obtains the same branch concurrency for every independent node without stream switches and events.
3. Measure both modes with one binary: GGML_CUDA_ANY_ORDER=1 vs default graphs. Expected: any-order wins by a wide margin (it targets ~13 ms of GPU idle vs ~1 ms of CPU launch overhead), and hipExtLaunchKernel's lower per-launch CPU cost (2.1 vs 2.96 us) recovers part of the graph benefit.
4. Optional later experiment (stage 5): if the stage-0 microbench shows that captured hipExtLaunchKernel nodes replay with overlap, allow capture in any-order mode; the design already makes that safe: decisions depend only on graph structure and addresses, both fixed per graph key (node_props check in ggml_cuda_graph_update_required), and scratch addresses are deterministic thanks to the ring reset per graph; a re-capture happens whenever properties change. Explicitly building a hipGraph DAG from the tracker's fence relation is NOT recommended (CLR would execute branches on parallel streams with signal joins).

MULTI-GPU (2 devices, scheduler layer split, cross-device copies via ggml_backend_cuda_cpy_tensor_async on the SRC stream + copy_event + dst stream wait; scheduler events in ggml_backend_sched_compute_splits, ggml-backend.cpp:1654+):
- State is per device: tracker, ring, stats live in each ggml_backend_cuda_context; each split is a separate graph_compute on its device with start fence/reset and end fence. The two GPUs run their splits sequentially (layer split), so any-order shortens each device's active window; it does not add cross-device overlap.
- Split input copies: cudaMemcpyPeerAsync/cudaMemcpyAsync are issued on the src device's stream AFTER that device's graph-end fence, so by the fence lemma all any-order kernels that produced the copied tensor are complete before the copy starts, independent of how ROCclr orders blits/SDMA (belt and braces: ROCclr also orders in-stream copies after prior packets). The event recorded after the copy is a barrier-AND packet with the barrier bit, and the dst stream's hipStreamWaitEvent is a barrier-AND packet that blocks all later packets on the dst queue, any-order ones included; in addition the dst split's first launch is ordered (graph-start fence).
- WAR on input_cpy across tokens (the src device overwrites the dst device's input buffer for token t+1 while token t's any-order kernels on the dst device might still read it): the scheduler orders this through its event chain (dst device records events after its split; the src device waits on them before the next copy); an event record completes only after all prior packets on its queue complete (barrier bit on the marker packet), so any-order kernels are covered. The stage-0 canary (c) verifies this HIP property explicitly; until it passes, the graph-end fence on the dst device also guarantees it.
- Host-side syncs (logits via tensor_get: memcpy + cudaStreamSynchronize; ggml_backend_synchronize) drain the queue completely (barrier packet + host wait), unchanged.
- Row-split mode (ggml_cuda_op_mul_mat, tensor split across devices with per-device streams and events) and allreduce.cu: launches on non-tracked streams => flags=0; unchanged semantics. Any-order gives no benefit there but stays correct.
- cudaStreamPerThread paths (buffer set/get/clear/cpy) are synchronous and unaffected.

## correctness_argument
ASSUMPTIONS ABOUT THE RUNTIME (HSA/ROCclr; each verified by the stage-0 canary):
A1 (in-order launch): packets on one HSA queue begin execution in queue order.
A2 (barrier bit): a kernel packet with the barrier bit does not launch until every preceding packet on the queue has completed, including their release fences (agent scope). hipExtAnyOrderLaunch clears the barrier bit of that packet only; flags=0 (and every <<<>>> launch) sets it.
A3 (in-stream commands): hipMemcpy*/hipMemsetAsync, hipEventRecord, hipStreamWaitEvent, hipStreamSynchronize on a stream are ordered after all previously submitted packets on that stream (blit kernels carry the barrier bit; SDMA copies and markers are barrier-AND packets or are preceded by one) and a barrier-AND packet blocks every later packet regardless of its barrier bit. The design does not rely on A3 for kernel-vs-kernel hazards; it relies on it only where today's code already relies on stream order (scheduler copies/events), and adds explicit fence kernels at graph boundaries so that even A3 is not load-bearing there.
A4 (memory model): a kernel's writes are visible to any kernel that launches after it completed (release at completion, acquire at launch, both agent scope, present in both packet headers). Concurrent kernels writing disjoint bytes do not corrupt each other (GPU L2 uses byte-masked writes; no false sharing at cache-line granularity).

LEMMA 1 (fence): if packet P_f has the barrier bit, then for all i < f and all j >= f, P_i completes before P_j launches. Proof: A2 gives it for j = f; A1 gives launch(P_j) >= launch(P_f) for j > f.

INVARIANT maintained by the tracker for the tracked queue: let F be the index of the most recent ordered launch (or the forced graph-start fence). epoch_w (epoch_r) is a superset of the bytes written (read) by every launch with index >= F.
- Ordered launch L: epoch := ranges(L) - holds because L is the new F and L is the only launch >= F.
- Any-order launch L: epoch += ranges(L) - holds trivially.
- Unknown launch (raw/library/memcpy): epoch += ranges - holds; not clearing keeps the superset property even though the launch was in fact a fence.
- Ranges(L) are supersets of the true byte sets: graph tensors (dst as r+w, srcs as r, all nodes of the fusion unit, view spans via ggml_nbytes), pool scratch (registered at alloc, before the first launch that could use it), hidden buffers (registered by their owners), intra-unit extra launches (ordered by default so they inherit the unit's ranges). Completeness of registration is the one obligation on op authors and is checked by the AO_VERIFY mode and test-backend-ops.

THEOREM (no data race): let L_a, L_b (a < b) be two launches on the queue that conflict (some byte is written by one and read or written by the other). Then L_a completes before L_b launches.
Case 1: a >= F_b (L_a was issued at/after the fence current when L_b was decided). By the invariant, L_a's ranges are in the epoch, so the decision rule (W_b overlaps epoch_w or epoch_r, or R_b overlaps epoch_w) makes L_b ordered; by Lemma 1 with f = b, L_a completes before L_b launches.
Case 2: a < F_b <= b. Lemma 1 with f = F_b gives completion of L_a before launch of P_{F_b}, and launch(P_{F_b}) <= launch(L_b) by A1 (equality if L_b is the fence itself).
In both cases, by A4, L_b observes all of L_a's writes, and a write by L_b cannot land before L_a finished reading (WAR is a conflict too). Intra-unit launches: the second and later launches of a unit are ordered (default policy) or explicitly declared independent by the op, so within a unit the original order is preserved wherever it matters. Cross-stream/cross-device: hazards are ordered by events/copies exactly as today (A3), and each graph is bracketed by a start fence (nothing older in flight when the ring is rewound and when the split's inputs are consumed) and an end fence (every producer of a tensor that the scheduler will copy or the host will read is complete).

BIT-EXACTNESS: each kernel is a deterministic function of its input bytes (intra-kernel atomics and reduction orders are unchanged since the kernels, their launch parameters and their launch order inside a node are unchanged). By the theorem every kernel reads exactly the bytes it would read under fully serialized execution and nothing overwrites its inputs before it finishes, so every output is bit-identical. The reorder pass changes only the position of provably independent units (source edges plus view-base relations, the same is_src_of test as Vulkan's ggml_vk_graph_optimize), i.e. a different topological order of the same DAG; it runs before ggml-alloc so buffer assignment is recomputed for the new order (addresses change, values do not).

SAFETY MARGINS: an unnecessary ordered launch only costs time; the only harmful error is an any-order launch with an incomplete range set. Defences: unknown launches never clear the epoch; the first launch of every graph is a fence; wrap-around or big pool allocations force a fence; GGML_CUDA_AO_PARANOID=1 fences before every non-wrapper op that overlaps the epoch; GGML_CUDA_AO_VERIFY=1 runs each graph twice (all-ordered, then any-order) and compares every node output; test-backend-ops and llama-perplexity are run with any-order on and off; AO_STATS exposes counts for review.

## risks
1. Runtime semantics (A1-A4) are inferred from HSA/ROCclr behaviour and the measured overlap, not from CLR source: e.g. whether hipEventRecord markers and SDMA copies always fence any-order kernels. Mitigation: stage-0 canary tests (a)-(c), graph-start/end fence kernels that make the scheduler paths independent of A3, PARANOID mode, and keeping the fences until the canary passes.
2. Incomplete range registration (a hidden buffer or an op that reads memory not listed in src[]) is the only way to get a data race. Mitigation: dst counted as read+write, unknown launches never clear the epoch, registration at every cudaMalloc/cuMem site (q8cache, hcb scratch, fattn f16 extra), AO_VERIFY double-run comparison, test-backend-ops in both modes, perplexity check; per-op denylist env (GGML_CUDA_AO_DENY=op,op) to bisect a suspect.
3. hipExtLaunchKernel marshalling differences: argument count must match exactly, HIP_STRICT trivially-copyable check, the header's GGL helper discards the error code. Mitigation: own helper that checks the hipError_t; compile-test on representative kernels in stage 0e; per-kernel fallback to <<<>>> (ordered) if something does not compile.
4. CPU overhead growth (dry-run matching, tracker scans, hipExtLaunchKernel) could make the host the bottleneck once GPU time drops toward 20 ms. Mitigation: hipExtLaunchKernel is cheaper than <<<>>> (2.1 vs 2.96 us), plan-cache caching of extents/signatures (stage 4), GGML_JOHNV8_TIMING monitoring.
5. Reorder pass side effects: longer lifetimes raise compute-buffer memory (bounded by the window), dry-run mis-detection of a fusion unit (allocation-dependent checks) could split a unit and lose a fusion, and the ggml-alloc in-place decisions change (values unaffected). Mitigation: compare fusion counts via GGML_JOHNV8_GRAPH_DUMP, window tuning, keep-pattern list mirrored from try_fuse, env kill-switch for the pass.
6. Losing HIP graphs and GRAPH_OPT in any-order mode (-3-4% from graphs) and possible CLR incompatibility if capture is ever enabled with hipExtLaunchKernel. Mitigation: hard mutual exclusion in code; stage-0 (d) before any attempt to combine.
7. Ring pool: dropping the LIFO assert for ring blocks could hide misuse; big prefill allocations fall back to the bump area with forced fences (prefill mostly ordered, small regression possible for long prompts); +64 MB VRAM per device; a too-small ring wraps often and fences. Mitigation: live-count debug assert, AO_STATS n_ring_wraps, GGML_CUDA_AO_RING_MB.
8. Performance surprises from overlap: two bandwidth-bound matvecs co-running may each get slower, and any-order kernels may steal CUs from the critical-path kernel; net effect must be measured, with the per-op denylist as a tuning knob.
9. Multi-stream code paths (row split, allreduce, GRAPH_OPT) share the context; an accidental any-order launch on a non-tracked stream would be unsafe. Mitigation: wrapper compares the stream pointer; assert curr_stream_no == 0 when the tracker is active.
10. Debuggability: asynchronous faults are attributed to a later launch; a GGML_CUDA_AO_SYNC_DEBUG mode (stream sync after each unit) restores attribution.
11. ROCm version dependence: hipExtAnyOrderLaunch behaviour or CLR's blit ordering could change across ROCm releases; keep the canary test in the tree and run it per upgrade.
